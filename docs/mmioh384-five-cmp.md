# BTC79X5: загрузка пяти CMP 50HX с BAR1 по 32 ГиБ

Дата проверки: 2026-10-13. Результат относится к конкретному стенду BTC79X5 и его модифицированному BIOS, а не ко всем платам X79.

## Проблема и результат

С четырьмя CMP система загружалась; добавление пятой CMP блокировало доступность системы после включения. Замена одной CMP на GT 710 возвращала загрузку. Отдельный контроль: четыре CMP **без GT 710** также успешно загрузились — обязательное наличие карты с видеовыходом исключено как причина в этой конфигурации.

После расширения MMIOH с 256 до 384 ГиБ система загрузилась сначала с четырьмя, затем с пятью CMP. Доступны SSH и NVIDIA-SMI. Размер BAR1 не уменьшали.

**Фактически проверено: четыре CMP по 20 ГБ + одна CMP на 10 ГБ; у всех пяти BAR1 32 ГиБ. Пять физических карт по 20 ГБ ещё не проверены.** Наличие полного BAR1 у пятой карты подтверждает выделение адресного ресурса, но не заменяет будущую проверку 5×20 ГБ и нагрузочную проверку.

## Изменение BIOS

В исходном 256G-образе инструкция `mov eax,0x80000000` задаёт множитель 2 ГиБ. При Setup MMIOH `0x80` (128), Manual, получается 256 ГиБ. Новый множитель `0xC0000000` — 3 ГиБ; итог 384 ГиБ. Селектор BAR1 остаётся `9` (32 ГиБ).

Изменены ровно два байта:

- ROM `0x6CD3C9`: `80 -> C0`, множитель MMIOH.
- ROM `0x6C4E59`: `59 -> 19`, контрольная сумма данных FFS.

FFS GUID: `5C08C7C8-24C2-4400-9627-CF2869421E06`, начало `0x6C4E48`, размер `0x6AA7E`. Перед патчем проверены идентичность PEI-модуля эталону, заголовок и контрольная сумма FFS. В исследованном коде произведение вычисляется беззнаковым умножением с 64-битным результатом; последующее вычитание также 64-битное. Увеличение границы подтверждено после реальной загрузки.

Это **не** увеличение физической VRAM и **не** изменение BAR1. Это расширение адресного пространства, выделяемого прошивкой. Предварительный расчёт выравнивания BAR был гипотезой; причинную модель распределения каждого моста отдельно не доказывали.

## Прошивка и проверка

На стенде сняты два совпадающих полных SPI-дампа MX25L6405. Патч применён к свежему локальному дампу, сохранив настройки конкретного сервера. После записи flashrom сообщил `VERIFIED`; дополнительное полное чтение SPI побайтно совпало с записанным образом. У flashrom первый метод стирания не сработал, альтернативный завершился успешно; итог проверен отдельным чтением.

После перезагрузки верхняя граница root MMIO изменилась с `0x383fffffffff` на ожидаемую `0x385fffffffff`. Затем сервер штатно выключен, установлена пятая CMP и выполнен холодный запуск.

Фрагмент журнала загрузки с пятью картами:

```text
Oct 13 21:22:33 kernel: pci_bus 0000:00: root bus resource [mem 0x440000000-0x385fffffffff window]
```

Это широкий ACPI root window; **не следует считать всю разность его границ размером MMIOH**. Значение 384 ГиБ относится к изменённому высокому пулу.

Проверка устройств:

```text
GPU  PCI         VRAM        BAR1
0    01:00.0     20480 MiB   32 GiB
1    02:00.0     20480 MiB   32 GiB
2    03:00.0     20480 MiB   32 GiB
3    04:00.0     20480 MiB   32 GiB
4    05:00.0     10240 MiB   32 GiB
```

NVIDIA-SMI/KMD: `610.43.03`, CUDA UMD: `13.3`. При проверке журнала этой загрузки совпадений `RmInitAdapter failed`, `NVRM: Xid`, `failed to assign` не найдено. Это проверка загрузки, не длительный тест стабильности. В следующем снимке NVIDIA-SMI на GPU 2 присутствовал процесс `rgminer.cuda12.turing`, 10 MiB; утверждать, что все сервисы оставались остановлены, нельзя.

## Публичный образ и воспроизводимость

- Образ: [`../firmware/rebar-xve-tu102-v2-mmioh384g.rom`](../firmware/rebar-xve-tu102-v2-mmioh384g.rom).
- Скрипт: [`../firmware/apply_mmioh384.py`](../firmware/apply_mmioh384.py).
- База — уже опубликованный `rebar-xve-tu102-v2-mmioh256g.rom`. Свежие частные SPI-дампы и NVRAM стенда не публикуются.

SHA256 публичного 384G-образа:

```text
76e2fab3cabc5655962d75e8b38f7d28de9eb135b5bd19f68e831da04ccc93cd
```

SHA256 реально прошитого образа на базе локального дампа:

```text
19e621884d2b0cac5691b80ced8aff1f969f12a344351c9c70a20c26ac4282b5
```

Полные образы различаются; **модифицированный PEI-модуль побайтно идентичен**. Скрипт на свежем дампе воспроизвёл реально прошитый образ целиком. Публичный ROM как полный образ отдельно на плате не прошивался.

Воспроизведение (выходной файл не должен существовать):

```bash
python3 firmware/apply_mmioh384.py \
  firmware/rebar-xve-tu102-v2-mmioh256g.rom \
  /path/to/new-mmioh384.rom
sha256sum /path/to/new-mmioh384.rom
```

## Предупреждение и восстановление

Неподходящий BIOS может сделать плату незагружаемой. Публичный ROM — эталон для конкретной платы, **не универсальный образ для прошивки X79**. Предпочтительный способ — патч собственного свежего SPI-дампа после проверки совпадения PEI-модуля; скрипт отклоняет неизвестный модуль и повторный патч.

До записи нужны два совпадающих дампа, внешняя копия оригинала, проверка модели платы/чипа и доступный аппаратный способ восстановления SPI, если POST пропадёт. Не отключать питание при записи. После записи — полное обратное чтение и сравнение, затем контрольная загрузка. Linux `pci=realloc` не исправляет зависание до загрузки ОС.

На стенде оригинальный дамп сохранён отдельно на двух машинах; при откате следует использовать именно собственный оригинал, а не дамп другого сервера.
